# Carromscore v3.4.10

Fixes a data-integrity bug that wrote negative per-board scores
into the archive for some multi-set matches.

**APK SHA-256**: `84b41e07b2a14677354d6281cfc851e590991bc99c94a4198742e7a0b36be0f5`

<!-- apk-required: false -->

Web changes only — existing v3.4.9 APK installs auto-update on
next launch. TWA bumped for parity; fresh APK download is optional.

## What changed

- **`endMatch()` reconcile-last-row logic** was summing the entire
  `boardLog` (all sets combined) but comparing against
  `sideA.points` / `sideB.points` — which reset to 0 at each
  SET+1 boundary. On multi-set matches, this produced a large
  negative adjustment written into the last board's row. Fix:
  scope the reconcile sum to the current set only.
- **Defensive `Math.max(0, …)` clamp** on all three boardLog
  snapshot paths (`adjustSets`, `adjustBoard`, `endMatch`). A
  per-board delta can never legitimately be negative under any
  real carrom rule — so the client refuses to write one, even if
  some future logic drifts.
- **~14 existing history records** carry the negative-row
  pattern from this bug. They rendered oddly in the history
  popup (winner sometimes flipped; per-set totals looked wrong).
  Data patches for those records are handled separately in the
  RTDB console; the code fix here prevents the pattern from
  reappearing on new matches.

## Migration notes

- **No RTDB rule changes**, no schema changes.
- **APK bump** (versionCode 57 → 58, versionName 3.4.9 → 3.4.10)
  for TWA parity; wrapper otherwise unchanged.
- **No forced client update** — the fix is purely on the score-
  keeping path. Users on older builds continue to score, but any
  multi-set match they finish on old code may still write a
  negative row.
